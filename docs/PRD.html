Beacon Manager

A central registry and control plane for every Beacon analytics deployment across every product — instances, products, and per-instance access, all in one place.

v1 Sibling to apps-analytics-sdk (Beacon itself)

1. Why this exists

Beacon started as one shared, multi-tenant deployment: one process, one database, every product a row. That's the right default and stays the default. But at real scale (20+ products, growing continuously), two things become true: some products eventually need real data isolation (their own dedicated instance, not just a row in the shared one), and someone needs one place to see and manage every instance that now exists — rather than bookmarking N separate dashboard URLs and N separate admin keys.

Beacon Manager is that one place. It is deliberately not a copy of any instance's analytics data — it holds a registry (which instances exist, which products live on which instance) and enough credentials to act on each instance's real admin API on your behalf.

2. Architecture

Manager DB (this repo's own Postgres)
  instances  — id, kind (shared|dedicated), origin_url, encrypted scoped credential, status
  products   — id, name, instance_id, remote_group_id (that instance's own project_groups.id)

Each registered Beacon instance
  — its own separate database, unrelated to Manager's
  — Manager holds one scoped admin_users credential per instance it manages,
    not the instance's master key

2.1 Registration & credential minting

Registering an instance takes a one-time bootstrap admin key for that instance. Manager uses it exactly once — to call that instance's own POST /admin/admin-users and mint a brand-new, scoped credential (role: admin, authProvider: manager). Manager stores only the newly-minted credential (AES-256-GCM encrypted under Manager's own key), and never persists or logs the bootstrap key. Every subsequent call to that instance uses the minted credential.

This makes Manager's access to any one instance independently revocable: removing an instance from Manager's registry deletes that one admin_users row on the target (best-effort — it still forgets the instance locally even if the target is unreachable), without touching the instance's own master key or any other credential.

2.2 Products

A "product" in Manager is a durable pointer: this name lives on this instance, as this group. Manager can create a product on a chosen instance directly (proxying that instance's own POST /admin/products — see Beacon's Phase 17), or adopt a product that already exists on an instance via sync, which reads that instance's project groups and tracks any marked kind: 'product'.

The cross-instance products view fans out live to each instance's real admin API for project counts and reachability — it never caches or duplicates analytics data.

3.1 Why the enforcement lives on Manager, not in the embed page

The embed page's browser-side code is not trusted for security — a determined visitor can read its JavaScript and craft arbitrary requests. The actual boundary is server-side, in Manager's /public/embed/* routes: every single request re-fetches that session's product's real, current project list from its Beacon instance and checks the requested project id against it before proxying anything. There is no cached or client-supplied "which product am I" — it is re-derived from the session token on every request. A session for Product A requesting Product B's real project id — even one it somehow learned — gets a 403, not a redacted response; verified directly against two real products on a real running Beacon instance, not just the fake test double.

4. What's explicitly not built yet

  • Dedicated-instance provisioning — Manager can register an already-running dedicated instance, but cannot yet stand one up itself (needs a hosting-provider integration; there is none in either repo today).
  • Migration — moving a product's data from a shared instance to a newly-provisioned dedicated one. A real, human-confirmed cutover process, not automatic.
  • Multi-user RBAC on Manager itself — v1 is single shared admin key, matching Beacon's own pre-RBAC starting point.

Each of the above is a real, separately-scoped phase — see ROADMAP.html.
