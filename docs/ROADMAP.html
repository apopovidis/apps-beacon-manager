Beacon Manager Roadmap

Phase B of Beacon's multi-product architecture — see the sibling apps-analytics-sdk repo's ROADMAP.html Phase 17 for Phase A (product modeling on the shared instance) and the discussion that shaped this whole roadmap.

Phase 1 — Registry + control plane v1

Proves the core mechanism end to end: register a real Beacon instance, mint a scoped credential, create and track products on it, all from one place — before any dedicated-instance provisioning or migration complexity gets added.

NowPhase 1
  • Instance registry — register, health-check, and remove Beacon deployments. Registration mints a scoped, revocable auth_provider='manager' credential on the target instance rather than storing its master key; removal best-effort revokes that credential remotely and always forgets the instance locally.
  • Cross-instance products — create a product directly on a chosen instance (one call, same UX as Beacon's own "New Product" flow), or adopt products that already exist on an instance via sync. The products view fans out live to each instance's real admin API — no cached/duplicated analytics data.
  • Proxied key rotation from Manager's own dashboard.
  • 13 automated integration tests against a hermetic fake-Beacon HTTP stub (registration, wrong-bootstrap-key rejection, duplicate-origin rejection, health check up/down, revoke-on-remove including the unreachable-instance case, sync-adopts-only-product-kind-groups, create-product, proxied rotation, unreachable-product reporting).
  • Verified live against a real running Beacon instance (not just the fake stub): registered it, confirmed the scoped admin_users row actually appeared in Beacon's own database with the right role/auth_provider, created a real product through Manager and confirmed the resulting project group + project rows exist in Beacon's real database, then removed the instance and confirmed the scoped credential was actually deleted on the Beacon side — not just forgotten locally.

Phase 2 — Embeddable, product-scoped /beacon UI

The agency use case: an outside agency manages one client's site and needs its own login into just that product's analytics, from that product's own domain — without touching Manager or any other product. Deliberately architected so the real dashboard and the real security boundary both live once, on Manager, and what a web app installs at its own /beacon is a thin pointer (an iframe) to it — the same pattern most embeddable analytics/support widgets use, and it avoids retrofitting scoping into Beacon's own ~80-route admin API.

NowPhase 2
  • Product-scoped logins — product_access_credentials (username + scrypt-hashed password, no new dependency) and embed_sessions (opaque 12h token). Completely separate identity from Manager's own admin key and from any Beacon instance credential — this identity can only ever reach one product.
  • The real security boundary is server-side, on Manager — /public/embed/* re-fetches that session's product's live project list from its Beacon instance and checks the requested project id against it on every single request, not once at login. A session's own product is never cached or client-supplied.
  • The hosted dashboard — GET /embed/:productId, a real login-gated page (project list, summary, recent events, 30-day web analytics) served by Manager itself.
  • embed-snippet/beacon.html — the actual file a web app drops at its own /beacon route; a one-line iframe pointer, works on any stack (static hosting, Express, Next.js — see its README), no backend logic to run.
  • Manager UI — "Embed access" per product: create/list/revoke agency logins.
  • 25 automated integration tests (up from 13, +12): login success/wrong-password/cross-product-login-rejected, missing/garbage/expired session tokens, scoped project list, scoped summary/events/web-analytics, credential revoke breaks future logins, duplicate username, short password — and critically, a Product A session requesting a real Product B project id gets 403, the core claim this whole phase rests on.
  • Verified live against two real products on the real running Beacon instance (not just the fake stub): created "Marketing Site" and "Internal Dashboard" as real products, granted an agency login to only Marketing Site, logged into the real hosted /embed/:productId page, confirmed the dashboard showed only Marketing Site's real data — then, from that authenticated browser session, directly requested Internal Dashboard's real project id and confirmed a 403 and that it never appeared in the scoped project list. Also verified the actual embed-snippet/beacon.html file end to end via a real iframe embed.
